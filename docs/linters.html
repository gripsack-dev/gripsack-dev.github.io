Linters

New IR8 workspaces use named check outputs attached to profile files, and task checks for invocation postconditions. See the 0.48 SDK check reference. Those are explicit command checks, not an automatic invocation of the embedded packs described below.

The lint field on this page belongs to the supported legacy host/module API. It checks config shape before deployment; it is not a workspace file option or a complete schema validator for every tool.

Linters are data: every shipped linter is a versioned data pack embedded in grip (crates/griplint/packs, key tables as TOML) checked by the in-crate engine in-process — no venv, no provisioning, no plugin lifecycle. lint: "name" travels in legacy module IR; grip check and grip apply run the linter with no additional runtime for embedded packs. External griplint-* executables retain the protocol path for formats not covered by the data engine.

The 0.48 source contains the 23 embedded packs below. A pack covers its recorded versions and rules, not every upstream setting or future version.

Using a linter

For legacy modules, first-party packs need no registration: lint: "helix" selects the embedded pack. External plugins register in env.toml; opt in from the module either way.

# Only needed for an external linter:
[linters.internal]
path = "/opt/bin/griplint-internal"     # explicit executable — the out-of-tree form

import { module, symlink } from "@gripsack/core";

export default module("yazi", {
  config: { "configs/yazi/yazi.toml": symlink("~/.config/yazi/yazi.toml") },
  lint: "yazi",
});
  • package is a plugin-store ref "owner/repo@tag": grip downloads the release binary, verifies it against the mandatory sha256 sidecar, and receipts it into $GRIPSACK_HOME/plugins/ — the tag is the pin. path is the explicit executable for development.
  • lint = "<name>" must resolve against the registry: an unregistered name is a hard eval error with the module-line span, never a silent skip. There is deliberately no PATH-discovery fallback — discovery is how configs end up silently unlinted on one machine and linted on another.
  • lint= is the entire opt-in; there are no per-entry file lists. The linter owns the tool's layout knowledge: one griplint-yazi covers yazi.toml, keymap.toml, and theme.toml, and ignores what it doesn't recognize.

The command surface

For legacy modules, the core runs linting after evaluation and semantic admission. These commands do not have identical side effects:

command behavior
grip check eval + IR sema + linters; no destination deployment or payload build, but source capture, private evaluation receipts and external-plugin provisioning can occur
grip plan validates frozen inputs and reports the diff against the current generation; use explicit grip update to refresh pins
grip apply an error-severity lint diagnostic fails eval before anything stages

Linters check static shape. Legacy verify contracts and workspace named checks execute commands at their declared lifecycle stages. grip check is not a blanket execution of all named workspace checks.

The lint flow

Embedded packs run in-process. External linters use the protocol below; both return diagnostics rendered by the core.

a typo'd key fails grip check with a span — before anything is staged, before the tool ever runs:

grip check — legacy eval + sema + linters
error[griplint-helix/A01]: unknown key [editor] 'scrollof'
  --> /home/you/env/configs/helix/config.toml:4:1
   |
 4 | scrollof = 5
   | ^ not a real key
  help: did you mean 'scrolloff'?

Writing a linter

A linter is a plain executable speaking NDJSON over stdio — one request per module–linter pair:

{"op": "lint", "paths": ["configs/yazi/yazi.toml", "configs/yazi/keymap.toml"],
 "tool_version": "25.5.31"}
  • paths is the legacy module's prepared config source set, post-tree() expansion, read from the captured source bundle.
  • tool_version comes from the host lockfile pin — the lock that pins the binary also pins the config schema. Unpinned, the linter uses its latest schema and warns.
  • Diagnostics come back in the shared shape — same snippet, colors, and codespacing as every other gripsack diagnostic. Codes are namespaced griplint-<tool>/<code> (e.g. griplint-yazi/A01); the core's E0xx range stays reserved. Plugins serialize; only the core renders — there is no second renderer.
  • Unknown files are ignored, never errors. A linter that chokes on a layout it doesn't recognize is a bad linter, not a bad config.
  • Death is never silent: a linter that crashes, hangs, or emits garbage surfaces as a diagnostic, not a missing check. The contract made executable: griplint-conformance and gripfetch-conformance — run your plugin against the suite and the envelope stops being prose.

Where linters live

In the gripsack repo as data: crates/griplint/packs — TOML packs keyed by tool version, read by the in-crate engine. External executables use the protocol above and run as trusted native code, not inside the TypeScript evaluator sandbox. A successful lint does not establish runtime safety or complete upstream compatibility.
